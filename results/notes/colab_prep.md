**`scripts/pack_for_colab.sh`.** Stages `src/`, `scripts/`, `configs/`, `tests/`, `pyproject.toml` and the split files (`data/pf/<grid>/splits_*`, `data/*/*/<grid>/splits_all`, for `GRIDS`, default case118_ieee, case500_goc, case2000_goc) plus a `BUNDLE_INFO.txt` (UTC date, git revision, number of dirty files). `dist/` is **not** in `.gitignore` (I did not edit it): add `dist/` before the next `git add -A`. The tarball currently sits in `dist/` untracked.

**`colab_gpu_timing.ipynb`.** Parameters cell, GPU check (fails without a GPU unless `DRY_RUN`), upload cell (tarball or Drive path), install cell, environment cell (versions, scatter backend, `env.json`), data cell, helper cell, timing cell, optional Newton cell, report cell, figure cell, zip/download cell, troubleshooting.
- Install: keeps Colab's torch, finds its version and CUDA tag, tries the torch-scatter wheel at `https://data.pyg.org/whl/torch-<X.Y.0>+cu<cuda>.html` (and the exact version), else a pure-PyTorch stand-in (same one as the delta notebook; the environment cell records which backend ran, because it affects timings slightly). Then graphkit `8a8defb` with `--no-deps`, the same dependency line as the delta notebook (pandas<3, scipy, pyarrow, huggingface_hub, mlflow, lightning, gridfm-datakit==1.1.0, ...), then `pip install --no-deps --ignore-requires-python -e` of the bundle (our `pyproject.toml` says `<3.13` and depends on `gridfm-graphkit`, which pip would otherwise try to resolve from PyPI and let it touch torch). Skipped if everything is already installed (`FORCE_INSTALL`). Prints `RESTART REQUIRED` if pip changed torch, numpy, pandas or scipy.
- Data: `snapshot_download` of `gridfm/pf_small_<grid>` partitions 0..4 (IEEE 118, GOC 500) and 0..1 (GOC 2000) into `data/pf/<grid>/raw`; split `splits_timing` is test = all, train/val = two dummy ids each.
- Timing (per model, via `load_genco(..., split_dir=...)`, model moved to CUDA): batch sizes 1, 16, 64, 256, 1024 built by cycling a pool of real scenarios (so batches larger than the dataset are fine); dtypes `auto` = fp32, bf16 and fp16 on pre-Ampere / TF32 on Ampere and newer; full 12 layers and 9-layer early exit (deep copy, `layers[:9]`, `num_layers = 9`); warm-up 3, 15 repeats (at least 10 even when slow, 60 s soft budget), median and quartiles, `torch.cuda.synchronize` around each call; peak memory; host-to-device copy timed separately (`clone` outside the timed region). OOM and other exceptions are recorded in `status`, larger batches of that configuration are skipped, the run continues. `MAX_BUSES_PER_BATCH = 1e6` skips batches too big by construction (GOC 2000 at 1024). Finished models are cached in `results/gpu_timing/partial` (idempotent re-runs, `FORCE`).
- Precision check: bf16/fp16/TF32 predictions against fp32 on 16 scenarios (max and median |dVm|, |dVa|, non-finite count), because a fast bf16 number is useless if the start is worse.
- Optional Newton cell: Jacobians at the flat start from `genco_certified.acpf` (modal size only, 181 unknowns), `torch.linalg.solve` in float64 and float32 on the GPU and on the host CPU for batches 1, 16, 64, 256, relative residuals, plus the scipy sparse LU per Jacobian on the host. The LU time doubles as a CPU-speed calibration against the M4 (0.0641 ms) so thresholds can be rescaled.
- Output: `genco_gpu_timing.csv` (kind, grid, size, device, dtype, batch, layers, ms_per_scenario, quartiles, ms_batch, reps, peak_mem_mb, status, note), `genco_precision_check.csv`, `report.md`, `genco_gpu_timing.png`, `env.json`, all in `genco_gpu_timing_<gpu>.zip`.
- Break-even constants (cell "Timing helpers"; sources in the comment): column `breakeven_same_solver_ms`, tol 1e-4, "measured" basis. `results/exp07/breakeven.csv` (paper set): full NR 0.306, compensated chord 0.0368, FDLF 0.0150 ms. `results/exp07/breakeven_stress_n5_base.csv` (N-5): 0.630, 0.0577, 0.0415 ms. These match the 0.31/0.04/0.015 and 0.63/0.06/0.04 figures in RESEARCH_LOG. M4 reference timings from `results/runtime/*.json` are embedded for orientation (GENCO CPU/MPS ms, LU 0.0641 ms).
- The report has one table per threshold set (IEEE 118; batch-1 latency, best ms per scenario and its batch, with host-to-device, ratio to each threshold, which solvers GENCO would beat), tables without thresholds for GOC 500/2000, the Newton table, the precision table and caveats.

## 2. Things the README warns about (found while reading, not fixed because outside my files)

- **Tag clash.** The delta notebook names run records and weights `control_s0`, `delta_vm_va_s0`, ... (no grid in the tag), exactly like `scripts/run_genco_delta.sh` for IEEE 118 (`results/genco_delta/runs/control_s0.json`, `checkpoints/finetuned/control_s0/`). Unzipping the Colab result in the repo root would overwrite the IEEE 118 matrix outputs. The README says to unzip into `results/colab/genco_delta_goc2000/` and to move the weights to `checkpoints/colab/` (git-ignored). Better long term: add the grid to the tag in the notebook (parameters cell, not touched by me).
- `pyproject.toml` has `requires-python <3.13`; Colab's Python may be newer, hence `--ignore-requires-python`.

## 3. Dry run (local, CPU, seconds)

The notebook has a `DRY_RUN` flag (IEEE 118 Base, 1 partition, 16 test scenarios, pool of 8, batch sizes [1, 4], fp32/bf16, 12 and 9 layers, 1 repeat, Newton pool of 6). I executed all code cells of the generated `.ipynb` in one process against the local data, with `nice`, 2 torch threads and the GPU job untouched:
- `GENCO_CERTIFIED_ROOT` pointed at a scratch root whose `checkpoints/`, `data/`, `src/` are symlinks to the project and whose `results/` is private, so `load_genco` did not rewrite the shared `results/configs/*.yaml` that the running matrix reads back (I checked their mtimes afterwards); `HF_HUB_OFFLINE=1`.
- Result: **all cells ran, 19 s wall**. 10 timing rows, all `ok`; precision rows for bf16 (12 and 9 layers); host LU 0.39 ms (6x the M4 value: the machine was loaded by the training job, so only the code path counts); Newton rows float64/float32 with relative residuals 7e-16 / 4e-7; report, CSVs, PNG and zip written. A second run exercised the "partial results exist, skip" path (read back from CSV, 6 s).
- Unit checks of `time_forward` with fake models: OOM message gives status `OOM`, other exceptions give `error: ...`, a good model gives `ok`; `precision()` for fp16/tf32/bf16/invalid names; the repeat-budget logic.
- Side observation (CPU, 8 scenarios, not a result): bf16 autocast moved the predicted Va by up to 0.09 rad (median 0.018 rad) and Vm by up to 0.03 p.u. against fp32. If that holds on a GPU, bf16 is a poor Newton start and the speed-up is moot; the precision table in the report is there to settle it.

To repeat the dry run: set up a scratch root as above and execute the code cells with `DRY_RUN = True` (replace the literal in the parameters cell).

## 4. Known risks and what is untested

1. **The pip steps on a real Colab runtime.** torch-scatter wheel availability for Colab's torch (the stand-in is the fallback), numpy/pandas upgrades forcing a restart, `gridfm-datakit` and `juliacall` (graphkit imports datakit at module level; first import may spend time on Julia packages). The delta notebook has the same exposure. If graphkit cannot import with Colab's torch (it pins 2.10 to 2.13), the troubleshooting cell says how to upgrade torch; the timing notebook keeps Colab's torch by default to measure what a normal user gets, which may differ from a torch 2.12 run.
2. **CUDA-only code is unexercised:** `get_device_capability`, peak-memory counters, `torch.cuda.OutOfMemoryError`, `empty_cache`, autocast on CUDA, `.to("cuda")` of the model and batches. The OOM path was tested with a mock. bf16 on a T4 (compute capability 7.5) may be refused, emulated (slow) or fine; fp16 is added automatically there, and fp16 could overflow (the precision table reports non-finite counts).
3. **Memory/time.** The 20 to 45 minute estimate is a guess. GOC 2000 at 256 scenarios, GOC 500 Base at 1024 and IEEE 118 Base at 1024 may OOM on a 15 GB T4 (recorded, not fatal). The first forward of a process is slow (CUDA init); warm-up absorbs it, but the first configuration's quartiles may be wider.
4. **Batches are built by repeating real scenarios.** GOC 2000 has only 400 downloaded scenarios, GOC 500 and IEEE 118 1,000. The forward pass does not depend on values; edge counts differ slightly between N-1 topologies, a second-order effect.
5. **Batch-1 latency is host-bound** (Colab's few vCPUs, Python overhead), and free-tier GPUs are shared, so repeat runs vary. The break-even thresholds are Python/scipy on one M4 thread; the notebook rescales with a measured LU ratio but a compiled solver would have lower thresholds still.
6. **Data layout assumptions** follow `scripts/fetch_data.py` (`gridfm/pf_small_<grid>`, Hive partitions of 200 scenarios, tables bus/gen/branch). The dry run covered IEEE 118 only; model loading with the test = all split and the GOC 500 / GOC 2000 downloads were not exercised (`scripts/bench_runtime.py` uses the same `load_genco` path for GOC 2000).
7. The early-exit rows use the same 9-layer truncation as `scripts/bench_runtime.py`; its +0.1 Newton iteration cost is noted in the report, not modelled.
